## 2. Classification Vocabulary And Method

The following labels are provisional governance labels from the existing Sprint 16 proposal:

- `PUBLIC`
- `INTERNAL`
- `RESTRICTED_WORKFORCE`
- `RESTRICTED_PATIENT`
- `RESTRICTED_SECURITY`
- `RESTRICTED_AUDIT`

Every inventory row separately records `Legal classification: NOT DETERMINED`. A proposed governance label is not a legal conclusion.

Technical statuses mean:

| Status              | Meaning in this inventory                                                                 |
| ------------------- | ----------------------------------------------------------------------------------------- |
| `STORED`            | Persisted by the implemented PostgreSQL schema                                            |
| `TRANSIENT`         | Accepted, returned, or processed in memory without being persisted as that representation |
| `DERIVED`           | Computed from other implemented records or verified inputs                                |
| `EMITTED`           | Written to an HTTP response or stdout/stderr boundary                                     |
| `CONFIGURATION`     | A named runtime setting or credential category; values are intentionally omitted          |
| `TEST ONLY`         | Synthetic fixture, identity, key, token, or configuration used only by tests              |
| `HYPOTHETICAL`      | Review question or future asset not currently implemented                                 |
| `ABSENT/PROHIBITED` | Verified absent from implemented schemas/contracts or explicitly prohibited by governance |

The register distinguishes PostgreSQL storage, API contracts, transient processing, workforce authority, configuration and secrets, diagnostics, migration metadata, test-only synthetic data, hypothetical future data, and absent/prohibited data. Hypothetical or absent assets are not described as currently collected.

## 6. OIDC And Workforce-Access Inventory

### Transient Token Boundary

- The API accepts bearer-token material only from the `Authorization` header and bounds it before verification.
- The verifier processes protected-header names `alg` and `kid`; required payload claim names `iss`, `aud`, `sub`, `sid`, `iat`, `exp`, `auth_time`, and `acr`; and optional timing claim `nbf` when present.
- Raw bearer material, token signatures, claims, `sid`, and MFA evidence are transient. They are not logged or copied into API errors.
- The API derives `sessionHash` by hashing `sid`; only the hash may be persisted.
- Tokens do not create roles, facility scopes, practitioner assignments, actor activation, or revocation state.

### Persisted Authority And Derived Context

| Boundary        | Implemented fields                                                 | Technical rule                                                                   |
| --------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| Subject linkage | `oidc_issuer`, `oidc_subject`, optional `practitioner_id`          | Controlled provisioning establishes the mapping; token identity only resolves it |
| Actor lifecycle | `is_active`, `activated_at`, `deactivated_at`                      | Current state must be active and activation cannot postdate authentication       |
| Role/scope      | `role`, optional `facility_id`, lifecycle timestamps               | Server-side assignments are authoritative; `PATIENT` is not an allowed role      |
| Session         | Hash, start/last-seen/absolute-expiry, revocation timestamp/reason | 30-minute inactivity and eight-hour absolute boundaries are enforced             |
| Request context | Actor/practitioner/session identifiers, roles, facility scopes     | Immutable, server-derived, request-local, and never accepted from request fields |

### Provisioning Input

Strict stdin-only variants support actor provision/activation/deactivation, practitioner binding, role assignment/deactivation, actor session revocation, and facility/practitioner/assignment revocation recovery. Inputs contain schema field names only as listed in INV-019. Command-line values are prohibited; interactive input is not echoed; success/failure emits only an aggregate affected count. No HTTP role-administration API exists.
